# M6 plan: auto-connect

Branch `m6-autoconnect`, based on `m5-tile` (#8). Implemented straight after the plan, per Baris's 2026-11-03 instruction. PLAN asks for the reviewer to approve the approach before the full build. That's skipped on Baris's say-so, and flagged in the PR.

## Approach (checked against current docs, 2026-11-04)

- **Association.** `CompanionDeviceManager.associate()` with a `BluetoothDeviceFilter` on the paired headphones' address (from `HeadphonesLocator`), single device. Android shows its own confirmation, and the app launches its `IntentSender`.
- **Presence.**
  - API 36+: `startObservingDevicePresence(ObservingDevicePresenceRequest)` with the association id.
  - API 31–35: the address form, which is deprecated in 36.
  - Needs `REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE`.
  - For Bluetooth classic, presence is the device connecting and disconnecting.
- **Wake-up.** `PresenceService : CompanionDeviceService` (exported, `BIND_COMPANION_DEVICE_SERVICE`).
  - On `EVENT_BT_CONNECTED` (`onDevicePresenceEvent`, API 36+; `onDeviceAppeared` before that), it starts `HeadphoneService`.
  - Starting a foreground service from the background is allowed for CDM apps that declare `REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND`. The docs prefer it over `REQUEST_COMPANION_RUN_IN_BACKGROUND`, which we don't request.
- **Connecting.** Unchanged. The service connects on the system's connected event, per the connect rule. The presence event only makes sure the service is running to hear it.
- **Stopping.** With auto-connect set up, `HeadphoneService` stops itself when both hold for 5 s:
  - the headphones are away (Disconnected, Bluetooth off, not paired, turned off, pairing mode)
  - no screen of ours is visible

  The next presence event starts it again. Without an association, the service keeps today's behaviour (up while away), because nothing else would restart it.
- **Contention.** Unaffected. AnotherApp, Lost and ConnectFailed aren't "away" (the ACL is up), so the service stays and waits for a user tap or a fresh connected event.

## UX

- A card under the hero when the headphones are paired, the phone supports companion devices, and there's no association yet:
  - "Connect automatically"
  - "Lets this app start when your headphones connect, so the tile and notification work without opening it first."
  - Set up / Not now
- Set up opens Android's dialog. Afterwards the card goes away.
- The notifications banner takes priority, so only one card shows at a time.

## Code

- `link/AutoConnect.kt`: support check, find the association for the headphones, request, observe. No addresses in logs.
- `service/PresenceService.kt`
- `service/ServiceLifetime.kt`: a pure `shouldStop(link, uiVisible, autoConnect)`, unit tested.
- `HeadphoneService` collects it, with the 5 s debounce. It also re-registers observation on start (idempotent).
- Manifest:
  - the two permissions
  - `uses-feature android.software.companion_device_setup` with `required="false"`
  - the service
- UI: `PhoneFeatures.autoConnect`, `Actions.setUpAutoConnect`, and the card.

## Tests

- **JVM:** `ServiceLifetimeTest` and the card's UI behaviour and golden.
- **Device (hands-off):**
  1. Set up from the card. adb taps Android's confirmation, since it's our own app's association on Baris's phone. Confirm with `cmd companiondevice list 0`, filtered to our package.
  2. Home, then Bluetooth off: the service stops within ~5 s and the notification goes.
  3. Bluetooth on, app not opened: the headphones reconnect and the presence event starts the service, which connects and loads (logcat).
  4. `am kill` (never force-stop), then repeat 2 and 3.
  5. `cmd companiondevice simulate-device-appeared <id>` as a second check of the wake-up path.
- Reboot auto-connect stays in H2 (not hands-off on this phone).

## Risks

- **R1.** The presence event may come before A2DP/HFP report connected. The 5 s debounce covers the gap, and the logs record the actual order.
- **R2.** A Bluetooth toggle may not fire presence events for an association made through the dialog. Fallback check: `simulate-device-appeared`. If real events never come, record it in FINDINGS and stop to ask.
