# S1 plan: source control spike

Branch `s1-sources`. The first commit (`216d2de`, local) applies the M3 review notes to PLAN.md. One PR into `main` at the end. The PR delivers findings and a recommendation, not a feature.

## Context

Baris's request (2026-10-28): switch explicitly between two sources (PC and phone), and stop a phone notification from taking the audio away from the PC for 3–5 s. The only fixes reported elsewhere are putting the earbuds away or turning off the phone's Bluetooth. S1 finds out whether BMAP can do it without auth:
- **Routing:** START [4.12].
- **Disconnect and reconnect:** [4.2] / [4.1].

Success means a reliable "use only this device" action and a reliable switch, which then get planned into a milestone after H1. If nothing works without auth, source control goes to "Never", with the evidence in FINDINGS.

## What's known

| Address | Source | Shape |
|---|---|---|
| 4.4 ListDevices | M0 | STATUS `01` + 5 × 6-byte MAC |
| 4.5 Info | M0 | STATUS `<MAC> 03 02 03 <name>`. The 3 middle bytes are unknown. |
| 5.1 Source | M0, bosectl | `[supported 2 B][active type][MAC if Bluetooth]`. M0 idle: `00 0f 00` (none active). |
| 4.12 Routing | bosectl | START `[0x82, MAC]` → RESULT with the now-active MAC. Reported to work only while both sources stream. |
| 4.1 Connect | bosectl | START with no payload → InvalidData ("needs MAC") |
| 4.2 Disconnect | bosectl | Name only. Payload unknown. |

## Tooling (debug build only, app code unchanged)

1. **`SpikeGuard`:**
   - adds START on [4.12], [4.1] and [4.2], only when the payload is `[0x82] + MAC` (4.12) or exactly `MAC` (4.1, 4.2)
   - only for MACs allowlisted for the session with `--es allow <MAC>[,<MAC>]`, and only if that MAC is in the [4.4] list
   - [4.12] allowed for the PC and phone MACs, [4.1] and [4.2] for the PC's only
   - fblock 18, [4.3], [4.7], [4.10] and [4.11] stay refused
   - MACs live only in the intent extras and local logs, never in code or commits
   - `BmapConnection.NEVER_SEND` is unchanged
2. **New `SpikeSession` commands** (same socket and `request()` pattern as M0):
   - `sources`: GET 4.4, then 4.5 for each MAC, then 5.1, logged with the MACs shortened to the last 2 bytes
   - `watch-source --ei ms 250 --ei seconds N`: polls 5.1 and logs each change with a timestamp
   - `route --es mac <MAC>`, `disconnect --es mac <MAC>`, `connect-dev --es mac <MAC>`: one guarded START each, logging the reply, then 5.1 and 4.5
   - `play --ei seconds N` / `stop`: a quiet sine tone on the phone through `AudioTrack` (`USAGE_MEDIA`), so the phone streams
   - `notify`: posts a notification on a debug channel with the default sound. This is the real trigger from Baris's report.
3. **PC audio:** PowerShell `System.Media.SoundPlayer.PlayLooping()` on a stock `C:\Windows\Media` wav, played to the default output device, then `.Stop()`. Nothing gets installed.
4. **D5 check** (M3 review): a debug extra `--es demoFail 1.11` sets `forceError[(1.11, GET)] = Runtime` on the demo's `FakeBmapDevice` (in `src/debug/.../DebugEntry.kt`).

Unit test: `SpikeGuardTest` (JVM). It checks:
- the never-send list and fblock 18 are refused
- [4.12], [4.1] and [4.2] are allowed only for allowlisted MACs and in the exact payload shape
- [4.1] and [4.2] are refused for the phone's MAC
- SET is refused everywhere

## Experiments (hands-off once the desk setup is ready)

The spike's socket takes BMAP from the service (expected, as in M2). After the run, a Bluetooth toggle restores the service. Before and after each experiment: `sources`. During each: `watch-source`.

- **E1. Inventory:**
  - [4.4] and [4.5] for every MAC
  - which entry is the PC: its [4.5] name matches the Windows computer name
  - compare the 3 unknown [4.5] bytes for connected and not-connected devices
  - [5.1] with nothing playing
- **E2. What [5.1] reports:** nothing playing, phone only, PC only, both (PC first, then phone, and the reverse).
- **E3. The notification steal:** PC streaming, phone silent, phone posts `notify`. Does [5.1] switch to the phone, after how long, and for how long? 3 runs.
- **E4. Routing:** [4.12] to the PC and to the phone in three states:
  - (a) one source streaming
  - (b) both streaming
  - (c) during an E3 steal

  Read [5.1] after each. 3 runs per case.
- **E5. Disconnect and reconnect:**
  - [4.2] with the PC MAC. Check [4.4]/[4.5] and [5.1].
  - Then a phone `notify` and `play`: does audio stay on the phone?
  - [4.1] with the PC MAC to bring the PC back. Check [4.5], and that PC playback returns to the headphones.
  - If [4.2] answers InvalidData, stop there and record it. No payload guessing.
- **E6. D5:** demo mode with `demoFail 1.11`, `cmd uimode night yes`, screenshot the failed Calls card, then restore night mode. If it's blank or unreadable, it's a real bug for M4. If not, record it in FINDINGS as a Robolectric quirk.

A reliable action is one that works 3 times out of 3, with [5.1] confirming the result.

## Desk setup (one batched ask, before E1)

1. Headphones on, connected to both the phone and the PC, with the headphones as the PC's default sound output.
2. Permission for me to run `powershell.exe` on the PC to play and stop a Windows wav, and to list the Bluetooth devices the PC sees (`Get-PnpDevice`). A read-only `Get-PnpDevice` was blocked by the auto-mode classifier while I wrote this plan, so this needs a yes from Baris or an allow rule. Nothing gets installed.

## Risks

- **R1:** [4.2] disconnects the PC and [4.1] fails to bring it back. Recovery: one click on "Connect" in Windows Bluetooth settings, or a power cycle of the headphones. That would be a second ask, so E5 runs last.
- **R2:** [4.2] could do more than disconnect (payload unknown). Unpairing is [4.3], which stays blocked. The guard allows only the exact `MAC` payload.
- **R3:** sound plays from headphones lying on the desk. Volumes stay low.
- **R4:** a long run lets the phone's screen lock. Debug window flags on `SpikeActivity` already handle that.
