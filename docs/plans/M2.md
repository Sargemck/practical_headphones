# M2 plan: connection service and state

Branch `m2-service`. First commit (`Apply M1 review notes`, pushed) applies the M1 review. One PR into `main` at the end.

## Context

M1 gave us a tested `:bmap` library and a simulated headphone. M2 puts it on the phone:
- a foreground service that owns the one RFCOMM connection
- a repository that turns the headphones into `StateFlow<HeadphoneState>`
- the connect and contention rules from M0/M1
- optimistic writes
- live updates
- the notification

It fixes Quiet Rebellion bugs 1 (first connect doesn't load) and 2 (ANC lag, our share). There's no new screen: M3 builds the UI on this state. M2 ends with a hands-off device run, including the first real-device test of the writes M1 couldn't verify.

## Design

Code under `app/src/main/java/io/github/sargemck/practicalheadphones/`. Rule for testability: everything with a decision in it is plain Kotlin with no Android imports, so it runs as a JVM unit test against `FakeBmapDevice`. Android classes are thin adapters.

### 1. Android adapters (`link/`)

- `RfcommTransport : FrameTransport` wraps a `BluetoothSocket`:
  - `read()` reads blocking on `Dispatchers.IO` into a 512 B buffer; `-1` returns null, an `IOException` passes through
  - `write()` writes and flushes
  - `close()` closes the socket, which also unblocks a pending read
- `RfcommConnector.connect(device): FrameTransport` with the CLAUDE.md connect rule:
  1. SPP UUID via `createInsecureRfcommSocketToServiceRecord`
  2. The connect counts only once GET 2.2 is answered (through `Headphones`)
  3. If SPP fails or doesn't answer: reflection `createInsecureRfcommSocket(2)`, same check
  4. The path used is logged. No loops: one attempt per path.
- `HeadphonesLocator`: finds the bonded device whose cached UUIDs include the BMAP UUID (M0 E8: it's advertised). Falls back to a name containing "QC Ultra". Remembers the address in SharedPreferences (never logged in full), so renaming the headphones (hardware test 1.2) doesn't lose them.
- `SystemLinkMonitor`: exposes `Flow<SystemLink>` (Bluetooth on/off, headphones' A2DP connected or not). It combines `BluetoothAdapter.ACTION_STATE_CHANGED`, `BluetoothA2dp.ACTION_CONNECTION_STATE_CHANGED` and an A2DP profile proxy for the initial state. The receiver is registered by the service.
- `BoseAppDetector`: `getPackageInfo("com.bose.bosemusic")` with a `<queries>` entry.
- `LogcatFrameLogger`: maps `:bmap` `LogEvent`s to tag `BMAP` with `elapsedRealtime` ms. Every frame in debug builds, errors only in release.

### 2. State (`state/`, pure Kotlin)

- `HeadphoneState`:
  - `link: LinkState`
  - per-section `Section<T>` (`Loading`, `Loaded(value)`, `Failed(message)`, `Unsupported`) for: device (name, firmware), battery, modes (configured modes only, current, favourites), audio (31.10), EQ, Self Voice, auto play/pause, auto answer, multipoint (read-only)
  - `boseAppInstalled`
  - The UI can never show a half-loaded section as real.
- `LinkState`: `BluetoothOff`, `NotPaired`, `Disconnected` (headphones off or asleep, quiet), `Connecting`, `Connected`, `AnotherApp`, `HeadphonesOff`, `PairingMode`, `ConnectFailed`, `Lost` (link unresponsive). The last four with a Reconnect button in M3; `AnotherApp` too.
- `LinkPolicy`: a pure reducer from (state, event) to (state, action). It holds the connect and contention rules:
  - Connect only when the system reports A2DP connected:
    - on service start if already connected
    - on a fresh connected event
    - on the user's Reconnect
  - Never retry on its own.
  - Socket `RemoteClosed` while the system still reports connected:
    - wait up to 2 s for a system disconnect or Bluetooth-off event (sleep and the BT toggle drop the socket around the same moment as the system event; M0 didn't record which comes first) (Q3)
    - if one arrives: `Disconnected`, quiet
    - if not, within 5 s of our power off / pairing mode: `HeadphonesOff` / `PairingMode`
    - otherwise: `AnotherApp`, no reconnect
  - `Unresponsive` or `IoError`: `Lost`, no reconnect.
- `HeadphoneRepository(connector, systemLink, scope, clock, logger)`:
  - **Initial load**, right after the connect check, one read at a time:
    1. `allModes()` (modes, current, favourites, 31.10 in one drain)
    2. battery, name, firmware, EQ, Self Voice, auto play/pause, auto answer, multipoint
    - Each section is set as it lands. A failed read is retried once (the library already retried timeouts), then the section becomes `Failed`. `Unsupported` maps to `Unsupported`.
  - **Modes offered** are only those with a name that isn't blank or `None`. `selectMode` refuses anything else.
  - **Optimistic writes:**
    - update state, send, reconcile with `WriteReply`
    - `Applied(value)`: set state to the value
    - `Raw`: confirm with one GET after the write (Q2)
    - failure: roll back and emit a `UserMessage` on a `SharedFlow` (M3 shows it as a snackbar)
    - 31.10 writes are built from cached state and conflated: while one is in flight only the latest desired value is kept, so a dragged slider sends at most one queued write
  - **Mode switch:** set current optimistically; `selectMode` returns the fresh 31.10, which replaces the cached copy.
  - **Live updates**, both ways (PLAN):
    - `unsolicited` frames go through the same read parsers into state (31.3, 31.8, 31.10, 2.2, 1.x)
    - polling behind `LiveUpdates.POLLING = true`:
      - UI visible: mode and 31.10 every 2 s, battery every 60 s
      - UI hidden: all three every 60 s, for the notification
    - Polling doesn't keep the headphones awake (M0 E0a) (Q5)
  - **Actions:** `nextFavouriteMode()` (pure helper: favourites ∩ configured modes by index, the next one after current, wrapping), `toggleAnc()`, `reconnect()`, `powerOff()`, `pairingMode()`. Power off and pairing mode are wired but only exercised in H1.
  - **Debug builds** log a one-line `STATE` dump on every change. Hands-off runs verify loading from logcat.

### 3. Service and notification (`service/`)

- `HeadphoneService`: foreground, type `connectedDevice`, not exported.
  - It owns the repository, the `SystemLinkMonitor` receiver and the notification.
  - It is started by `MainActivity.onStart` via `startForegroundService`. It keeps running while the headphones are asleep, off, or Bluetooth is off, showing a quiet "Not connected" notification, so it can catch the next connected event (Q1).
  - `MainActivity` reports UI visibility (onStart/onStop) for polling.
- `NotificationModel`: a pure mapping from state (title = name, text = battery and mode, or the link message). Actions "Next mode" and "ANC on/off" are PendingIntents to the service.
- Manifest:
  - permissions `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`
  - `<queries>` for `com.bose.bosemusic`
  - the service entry
- `MainActivity`: requests `BLUETOOTH_CONNECT` and `POST_NOTIFICATIONS` if missing (hands-off installs use `-g`), then starts the service. No new UI beyond that.

### 4. `:bmap` addition for the hardware test (Q4)

`QcUltra2.Experimental.multipointRaw = WriteFeature<Int, Multipoint>(1.10, raw byte)`, documented as hardware-test only and not used by app code. It keeps the rule that only config-defined features are sent.

## Tests

**JVM (`app/src/test`, JUnit 6, virtual time, `FakeBmapDevice`):**
- `LinkPolicyTest`: every transition above, including:
  - no connect without system connected
  - no reconnect after `AnotherApp` / `Lost` / `ConnectFailed`
  - the 2 s grace (a system disconnect after 1 s gives `Disconnected`, none gives `AnotherApp`)
  - the 5 s window after power off / pairing mode
  - Reconnect only with system connected
  - fresh connected event connects once
- `HeadphoneRepositoryTest`:
  - initial load fills every section from the fake
  - one silent address gives that section `Unsupported` and the rest load
  - an ERROR read retries once, then `Failed`
  - sections stay `Loading` until loaded
  - only configured modes offered; `selectMode` on a None slot refused
  - optimistic write then `Applied` reconcile; `Raw` confirmed by GET; ERROR rolls back and emits a message
  - 31.10 conflation: 10 rapid writes send ≤ 2 frames, and the final state is the last value
  - mode switch replaces 31.10 (spatial 02 → 00 as in E5)
  - unsolicited 31.10 / 2.2 frames update state
  - polling cadence for visible vs hidden UI; polling off with the flag
  - fake disconnect during load leaves no section shown as loaded with stale data
- `NextFavouriteTest`, `NotificationModelTest`: pure mappings.

**Instrumented hardware test (`app/src/androidTest`, JUnit 4, real headphones):** `HardwareWriteTest`:
1. stops our service
2. connects with `RfcommConnector`
3. reads all
4. then for each write in PLAN M2: read, write, read back, restore, with every reply frame and the time from write to confirmed read-back logged under `BMAP HW`:
   - 1.2 name: test name, then the original
   - 1.7 EQ: one band at a time
   - 1.11 Self Voice
   - 1.24, 1.27
   - 31.8 favourites: the current value written back
   - 1.10 multipoint exploration: current raw value, then bit 0x02 flipped, then restore

Restores run in `finally`. If a restore fails, the test fails and stops. It never sends 31.6, 4.8 or 7.4. The logged reply frames decide which writes switch from `Raw` to parsed `Applied` (recorded in FINDINGS; switching is a one-line config change in the same PR).

## Hands-off device run (desk setup only)

0. Start checks: headphones connected; if asleep, wake them with a spike connect, then close it.
1. **Hardware test:** `./gradlew connectedDebugAndroidTest`. Results go to FINDINGS (reply shapes, multipoint meaning, write → read-back times).
2. **Cold start ×10:** `am force-stop`, then `am start`. Each run's `STATE` dump shows every section `Loaded` (or `Unsupported`), with the time to fully loaded logged.
3. **Optimistic write timing:** toggle ANC via the notification action and log the time to the device reply (bug 2 baseline vs Quiet Rebellion's lag).
4. **Notification actions** via `cmd statusbar expand-notifications` + uiautomator tap:
   - "Next mode" and "ANC on/off"
   - state change confirmed by the device reply and the next state dump
   - original mode and ANC restored afterwards
5. **Bluetooth toggle off/on**, app not opened: notification goes "Not connected", then the service reconnects on the A2DP connected event. Time logged.
6. **Contention:** open a spike connect while the service is connected. The service goes to `AnotherApp` and does not reconnect for 60 s (logcat).
7. **Sleep:** leave idle until the 10.5 min drop. State goes `Disconnected` (not `AnotherApp`), no connect attempts afterwards. This records which comes first, socket -1 or the A2DP event, and goes into FINDINGS.

## Open questions for the reviewer

- **Q1. Service lifetime.** PLAN says "clean stop when the headphones disconnect" and also "BT toggle: service reconnects without the app being opened". Both can't hold before M6: a stopped service can't hear the reconnect, and a broadcast can't start a foreground service from the background. I read "clean stop" as closing the socket and going quiet (notification "Not connected"), with the service staying up until M6 replaces this with presence-based start and stop. OK?
- **Q2. Raw write replies.** For writes whose reply shape isn't verified, M2 confirms with one GET after the write. It's read-after-write, not the forbidden read-before-write. The hardware test then switches verified features to parsed replies, which drops the extra GET. OK?
- **Q3. Socket drop vs system event order.** M0 didn't record whether the socket's `-1` comes before or after the A2DP disconnect when the headphones sleep or Bluetooth turns off. Without a grace period, sleep could be misread as "another app". 2 s grace, then decide; the run measures the real order. OK?
- **Q4. Multipoint exploration** needs a raw 1.10 write: `QcUltra2.Experimental.multipointRaw`, used only by the hardware test. OK, or should it live in the test with a test-only hook?
- **Q5. Polling cadence:** 2 s for mode and 31.10 while the UI is visible, 60 s for everything when it's hidden, battery every 60 s. OK as a starting point until H1 decides?
